# Каркас и поэтапная реализация Pilot Flow Backend

## Назначение

Нужно превратить существующий handoff-пакет в работоспособный backend выбора пилотного производственного потока. Backend обслуживает уже спроектированный frontend, хранит версии анализа в PostgreSQL, рассчитывает допуск и рейтинг на сервере, формирует документы и фиксирует неизменяемое решение.

Работа выполняется в основной ветке `main`. Материалы разделяются каталогами, а не ветками.

## Исходное состояние

В репозитории отсутствует ASP.NET-приложение. Сейчас в нём находятся:

- OpenAPI 3.0.3 с 45 операциями и 51 схемой;
- PostgreSQL-схема с 13 предметными таблицами, ограничениями, триггерами и представлением;
- mock-сервер только для чтения;
- контрольный пример, acceptance-векторы и результаты проверки контракта;
- handoff, Swagger UI и карта соответствия экранов API.

OpenAPI остаётся авторитетным HTTP-контрактом. `schema.sql` остаётся авторитетной исходной схемой до появления первой управляемой миграции.

## Выбранный подход

Пользователь выбрал контрактный каркас прежде хранения и предметной логики. Реализация идёт четырьмя последовательными этапами.

1. Полный HTTP-каркас всех операций OpenAPI.
2. PostgreSQL, миграции и слой хранения.
3. Предметная логика и рабочие сценарии API.
4. Вспомогательные сервисы, экспорт и эксплуатационная готовность.

### Рассмотренные альтернативы

**Сначала предметная логика.** Раньше снижает риск ошибок расчёта, но не даёт frontend полной поверхности API. Не выбран из-за заданного порядка.

**Сначала полный HTTP-каркас.** Даёт стабильную структуру всех 45 операций и позволяет проверять совпадение с OpenAPI ещё до реализации поведения. Выбран пользователем.

**Сначала БД и CRUD.** Быстро закрепляет хранение, но заставляет принимать транспортные решения без цельного каркаса и откладывает проверку интеграции с frontend. Не выбран.

## Цели

- Создать собираемое и запускаемое ASP.NET Core приложение на .NET 10 LTS.
- Сохранить все 45 путей, методы, operationId, security-требования и типы ошибок OpenAPI.
- Сделать незавершённость явной: заглушка возвращает `501 application/problem+json` с кодом `NOT_IMPLEMENTED`.
- Поднять PostgreSQL 18 для локальной разработки и интеграционных тестов.
- Перенести существующую схему в управляемую последовательность миграций без потери ограничений и триггеров.
- Реализовать optimistic concurrency через ETag и `If-Match`, фильтрацию по владельцу и неизменяемые решения.
- Реализовать допуск, шесть критериев, прямой выбор, фиксацию и fork по правилам handoff.
- Проверить контрольный пример «Север» и все acceptance-векторы автоматическими тестами.
- Подготовить PDF-комплект из протокола, матрицы семейств и матрицы выбора.

## Не входит в обязательный объём

- Frontend и изменение предоставленного дизайна.
- Интеграция с 1С.
- Электронная подпись.
- Отдельные кабинеты участников и полноценный workflow согласования.
- Микросервисы, брокер сообщений и отдельный BPM-движок.
- Запуск макросов или автоматическое доверие формулам XLSM.
- Свободный графический редактор технологической карты.

## Антицели

- Не выдавать заглушки за готовую бизнес-логику.
- Не дублировать расчёты в контроллерах, SQL и PDF-проекции.
- Не заменять неизвестные значения нулями.
- Не менять enum, nullable-поля, decimal-строки или ошибки отдельно от OpenAPI.
- Не использовать `double` или `float` для предметных чисел.
- Не создавать универсальный фреймворк поверх одного продукта.

## Архитектура

Приложение является модульным монолитом. Зависимости направлены внутрь:

```text
PilotFlow.Api -> PilotFlow.Application -> PilotFlow.Domain
PilotFlow.Infrastructure -> PilotFlow.Application + PilotFlow.Domain
PilotFlow.DbMigrator -> PilotFlow.Infrastructure
PilotFlow.Api -> PilotFlow.Infrastructure (только composition root и регистрация DI)
```

`Domain` не зависит от ASP.NET, EF Core, Npgsql, PDF-библиотеки или текущего времени. `Application` координирует транзакции и работает через интерфейсы. `Infrastructure` реализует хранение, документы, часы, идентификаторы и канонический JSON. `Api` отвечает только за HTTP, авторизацию, валидацию транспортной формы и преобразование результата.

Ссылка `Api -> Infrastructure` разрешена только в startup/composition root. Endpoint-файлы не используют DbContext, SQL или инфраструктурные реализации напрямую.

## Этап 1 Полный HTTP-каркас

### Результат

- solution и проекты собираются на .NET 10;
- `global.json` фиксирует семейство SDK 10;
- центральное управление версиями NuGet-пакетов включено;
- все 45 операций зарегистрированы в `/api/v1`;
- route, HTTP method и operationId сверяются с `contracts/openapi.json`;
- Swagger UI использует авторитетный файл контракта;
- незавершённые операции возвращают единый `501` Problem Details;
- добавлены `/health/live` и `/health/ready`, не входящие в предметный контракт;
- JSON использует camelCase, строковые enum и согласованные decimal-строки;
- неизвестные маршруты дают стандартный `404`, а не `501`.

### Организация endpoints

Minimal API route groups группируются по ресурсу: identity/rules, analyses/versions, products, operations, families/routes/assignments, evaluation, protocol/selection, decisions/export. Каждая операция получает metadata с `operationId` из OpenAPI и в дальнейшем делегирует одному application handler.

На этапе каркаса не создаются фиктивные успешные ответы. Общий stub handler возвращает `501` с `code=NOT_IMPLEMENTED`, `traceId` и пустым `issues`.

### Аутентификация

Контракт сохраняет Bearer security. Production-конфигурация использует JWT Bearer с обязательными `Authority` и `Audience`. В интеграционных тестах используется подменяемая test-схема. Development bypass не включается автоматически, чтобы случайно не выпустить сервер без проверки личности.

## Этап 2 PostgreSQL и хранение

### База и миграции

Локальная среда использует PostgreSQL 18 в Docker Compose. Minor-версия фиксируется на актуальном исправлении выбранного major. Пароли разработки задаются локальными переменными окружения и не попадают в Git.

`contracts/schema.sql` превращается в миграцию `V001` без изменения семантики. Мигратор:

- применяет миграции строго по порядку;
- использует advisory lock;
- хранит номер, SHA-256 и время применения;
- отказывается продолжать, если уже применённая миграция изменилась;
- не запускается неявно при старте каждого экземпляра API;
- выполняется отдельной командой или контейнером перед API.

### Доступ к данным

Используются EF Core и Npgsql. Обычные запросы и отображения выполняются через EF Core. CAS-обновления revision, блокировки `FOR UPDATE`, finalize и массовое копирование fork оформляются явным SQL внутри инфраструктуры, потому что их корректность зависит от порядка операторов и числа изменённых строк.

Для каждой операции сначала проверяются владелец анализа и принадлежность UUID одной версии. Чужой ресурс маскируется как `404`. App-role не владеет схемой и не имеет DDL, TRUNCATE или обхода RLS/триггеров.

### Конкурентность

Все изменения агрегата требуют `If-Match`. Парсер принимает только ETag формы `"v:{versionId}:r:{revision}"`. Отсутствие заголовка даёт `428`, устаревшая revision — `412`. Успешная запись меняет revision ровно один раз и возвращает новый ETag. Автоматический повтор устаревшей команды запрещён.

## Этап 3 Предметная логика и рабочий backend

Рабочие HTTP-операции реализуются тонкими ASP.NET Core контроллерами по ресурсам. При переносе каждой операции её регистрация в каталоге заглушек удаляется. Маршруты, operationId, JWT, проверки `If-Match` и формат ошибок сохраняются и проверяются тестами OpenAPI.

Реализация идёт вертикальными группами, но остаётся в следующем общем порядке:

1. analyses, versions и identity/rules;
2. products, operations и product routes;
3. families, suggestions, assignments и family routes;
4. metrics, financial aggregation и admission;
5. six-criterion evaluation и provisional state;
6. selection, protocol, validation и preview;
7. finalize, immutable decision и fork;
8. list/detail/export projections.

### Правила расчёта

Единственным источником расчёта является доменный сервис с версией правил `fck-2026-tz-v1`. Он должен сохранять различие `null` и `0`, работать с `decimal`, выдавать причины и объяснение каждого балла.

Допуск проверяет долю выручки не ниже 10 процентов, длительность каждой позиции не более 30 календарных дней и включение каждой позиции в производственный план. Любое известное нарушение даёт `excluded`; без нарушения при пропусках получается `unknown`; полностью пройденная проверка даёт `admitted`.

Рейтинг сравнивает только допущенные потоки, применяет dense rank и шесть фиксированных критериев. Неизвестное значение в относительном критерии делает зависимые оценки предварительными. Отрицательный рост и максимум отрицательной маржинальности остаются unresolved согласно текущей версии правил, а не получают придуманную оценку.

Выбор первого места не требует порога 7. Второе место требует минимум 7 баллов и непустого обоснования обстоятельства вне шести критериев. Третье место запрещено. Прямой выбор не включается автоматически только потому, что остался один допущенный кандидат.

### Неизменяемость

Finalize повторно рассчитывает агрегат в одной транзакции, проверяет полноту и реквизиты, создаёт канонический снимок и SHA-256, вставляет Decision и переводит версию в fixed. После фиксации изменения создаются через fork; старый снимок и повторный экспорт не меняются.

### Готовность к finalize

Общие условия для всех режимов:

- версия находится в `draft`, пользователь является владельцем, `If-Match` актуален;
- заполнены название анализа, предприятие, дата начала проекта и все четыре применимые периода;
- общая выручка положительна, сверка выручки не имеет превышения, остаток учтён или объяснён;
- вся не-Other продукция распределена ровно в одно непустое подтверждённое семейство;
- у выбранного семейства заполнены границы и подтверждён маршрут;
- выбранный поток допущен;
- заполнены номер и дата соглашения, стороны, место, номер и дата протокола, составитель, утверждающий и выводы;
- заполнен `managerDecisionReference`;
- отсутствуют validation issues уровня error.

Для `ranked` дополнительно требуются завершённая непредварительная оценка, `canFinalizeRanked=true`, выбор первого или допустимого второго места и обоснование для второго места или равных лидеров. Для `monoproduct` требуются подтверждённая полнота номенклатуры и evidence основания. Для `dominantProduct` дополнительно требуются полный перечень продуктов, строго более 20 процентов выручки, преимущество не менее чем вдвое над каждым другим продуктом и единственный dominant product в выбранном семействе.

ИНН, список участников, `familyConclusions` и `rankingConclusions` остаются необязательными, если они не нужны для выбранного режима и печатных реквизитов. Это проектное решение до отдельного требования заказчика.

### Канонический snapshot

Перед RFC 8785 все decimal-строки приводятся к единственной записи: без ведущего плюса, без незначащих ведущих и конечных нулей, без десятичной точки у целого, с `0` вместо отрицательного нуля. Например, `"30.0"`, `"30.000000"` и `"030.00"` дают `"30"` после успешной валидации входа.

Массивы snapshot формируются в детерминированном порядке: сущности по UUID, маршруты по владельцу и position/occurrenceId, критерии в фиксированном порядке шести правил, issues по severity/code/path/entityId. Порядок участников сохраняет пользовательский порядок. Хэш считается только после такой проекции. Формат draft-ответов и примеров OpenAPI не обязан менять представление строк; канонизация относится к snapshot и его hash.

## Этап 4 Вспомогательные сервисы

- генерация PDF из единой protocol projection;
- канонизация JSON по RFC 8785 для снимка;
- clock, UUID generator и current-user abstractions;
- structured logging, traceId и безопасное логирование ошибок;
- readiness-проверка PostgreSQL;
- конфигурационная валидация при старте;
- контейнеризация API и мигратора;
- импорт XLSM только после завершения основного ручного сценария;
- эксплуатационная документация и примеры запуска.

PDF черновика помечается как черновик. PDF решения формируется только из сохранённого snapshot. Повторный экспорт не меняет дату протокола или значения.

`GET .../versions/{versionId}/export?draft=true` разрешает неполный документ и ставит заметную отметку `ЧЕРНОВИК`. `draft=false` требует полной готовности проекта документа, но всё равно ставит отметку `ПРОЕКТ` и не выдаёт его за принятое решение. Только `GET .../decisions/{decisionId}/export` строит неизменяемый комплект принятого решения из snapshot.

В репозитории нет эталонного PDF-шаблона. Первая версия использует профессиональный нейтральный A4-макет без выдуманного брендинга, с кириллическими шрифтами, тремя явно разделёнными документами и повторяемыми заголовками таблиц. Контрольный пример становится визуальным baseline после ручной проверки. Появление официального шаблона будет отдельным изменением требований.

## Формат ошибок

Ошибки возвращаются как `application/problem+json` и содержат:

- `type`, `title`, `status`, `detail`, `instance`;
- стабильный `code`;
- `traceId`;
- `issues` с JSON Pointer, сообщением и подсказкой исправления.

Форматные ошибки дают 400, отсутствие входа 401, отсутствие ресурса или доступа 404, конфликт состояния 409, stale revision 412, предметная валидация 422, отсутствие `If-Match` 428.

## Тестовая стратегия

### Этап 1

- contract test сравнивает множество method/path/operationId из OpenAPI с EndpointDataSource;
- каждый endpoint проверяется на `401` без identity или `501` с test identity;
- Problem Details и content type проверяются отдельно;
- health endpoints проверяются вне `/api/v1`.

### Этап 2

- интеграционные тесты запускают PostgreSQL-контейнер;
- проверяются все 19 существующих инвариантов схемы;
- два параллельных изменения дают один успех и один `412`;
- owner isolation и cross-version UUID проверяются отрицательными тестами;
- изменённая применённая миграция обнаруживается по hash.

### Этапы 3 и 4

- каждый acceptance-вектор сначала оформляется падающим тестом;
- контрольный пример даёт 13, 12, 7.5 и исключённый поток;
- `null` никогда не превращается в 0;
- документ и API-проекции строятся из одного результата;
- finalize/fork/export проверяются сквозными тестами;
- PDF проверяется по структуре и визуально на контрольном примере.

До использования `control-example.json` как финализируемой фикстуры исправляются явные противоречия handoff-правилам: при ручном `loadPercent` поля `loadActual/loadCapacity/loadUnit` остаются `null`, а при `laborMode=manual` поля `directLaborHours/outputQuantity` остаются `null`. Валидация не ослабляется ради ошибочно скопированных значений. Сам контрольный финансовый и рейтинговый результат не меняется.

## Проверка качества и готовность этапов

Каждый этап заканчивается успешными `dotnet build`, `dotnet test`, проверкой форматирования и обновлением README. Этап считается готовым только при отсутствии скрытых заглушек: каждая незавершённая операция либо явно возвращает `NOT_IMPLEMENTED`, либо полностью проходит свои контрактные и предметные тесты.

## Принятые технические решения

- .NET 10 LTS вместо более нового .NET 11 STS ради длинного окна поддержки.
- PostgreSQL 18 вместо только что вышедшего PostgreSQL 19 ради более зрелого supported major.
- Minimal APIs для каркаса и служебных маршрутов. Для рабочих операций команда выбрала тонкие контроллеры по ресурсам.
- EF Core для отображений и обычных запросов; явный SQL для CAS/finalize/fork.
- Отдельный мигратор вместо автоматической миграции при старте API.
- JWT Bearer в production; test authentication только в тестовом host.
- Один модульный монолит вместо микросервисов.

## Решения, оставленные реализатору

- конкретная поддерживаемая PDF-библиотека после небольшого технического spike;
- конкретный формат snapshot canonicalization implementation при обязательном результате RFC 8785;
- внутреннее разбиение route-group файлов, если сохраняются заданные границы модулей;
- конкретный способ запуска PostgreSQL-контейнера в тестах при воспроизводимости в CI.
